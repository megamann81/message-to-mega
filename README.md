### Moderation

Message submission is intended to pass through the Supabase Edge Function:

```text
/functions/v1/moderation-function
```

The moderation system is designed to handle checks such as:

- Blocked words and phrases
- Promotional/spam phrases
- URLs
- Email addresses
- Phone numbers
- Repeated characters
- Suspicious unbroken text
- Excessive punctuation
- Unsafe HTML/script patterns
- Per-IP message limits
- Submission cooldowns

Server-side moderation should be treated as the authoritative protection. Browser-side moderation is only an additional convenience layer.

## Message length

The message character counter is intended to use the maximum configured by the backend Edge Function rather than requiring a separate hard-coded frontend limit.

The page requests the limit with:

```text
GET /functions/v1/moderation-function
```

and uses the returned `maxMessageLength` value for the visible counter.

>**Authors note:** *You don't get to see the backend and you can't change this but you can gmail me at luke.ib.bronson@gmail.com if you would like the backend code because it's not provided in this repo. The values mentioned here are changed over there.*

## Message-rate protection

The backend can be configured with editable values such as:

```javascript
const MAX_MESSAGE_LENGTH = 1000;
const MAX_MESSAGES_PER_IP = 15;
const MESSAGE_COOLDOWN_SECONDS = 30;
const MAX_NAME_LENGTH = 80;
```

These should remain server-side so visitors cannot bypass them by editing the HTML.

>**Authors note:** *This is also in the backend, so don't bother looking for it in the HTML file.*

## IP privacy

The intended design stores a hashed representation of the visitor IP rather than the raw IP address in the `messages` table.

The backend uses a secret salt stored in Supabase Edge Function secrets and hashes the IP before storing it as `ip_hash`.

Do not expose the hash salt in the HTML or in client-side JavaScript.

## Database

The `messages` table is expected to contain these relevant fields:

```text
id
name
message
created_at
status
moderation_reason
pinned
ip_hash
```

Typical approved messages use:

```text
status = approved
```

Pinned messages use:

```text
pinned = true
```

The frontend reads approved messages ordered by:

1. `pinned` descending
2. `created_at` descending

## Analytics

The site can optionally record lightweight page/form events in:

```text

```

Examples include:


## Deployment

The project can be hosted as a normal static HTML site, provided the Supabase project and Edge Function are configured correctly.

A typical setup is:

1. Put the HTML file in the GitHub repository.
2. Configure the Supabase `messages` table.
3. Configure any required RLS policies.
4. Create/deploy the `moderation-function` Edge Function.
5. Add backend-only secrets in Supabase Edge Function secrets.
6. Make sure the Edge Function points to the same Supabase project used by the website.
7. Publish the static site through GitHub Pages or another static host.

## Secrets

The following kinds of values are **server-only** and must never be committed to the HTML:

```text
SUPABASE_SERVICE_ROLE_KEY
IP_HASH_SALT
```

Only the public/publishable key belongs in the browser.
